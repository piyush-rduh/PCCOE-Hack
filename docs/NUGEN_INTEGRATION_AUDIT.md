# AGCRO NuGen AI Integration Audit

**Audit date:** 2026-11-05  
**Scope:** Static inspection of the current repository. No application source, configuration, or test files were changed; this report is the only file added. This audit does not inspect a separately deployed website's runtime environment or network traffic.

## Verdict

**MOCK / SIMULATED ONLY**

The repository does not make an HTTP request to NuGen or any external AI inference provider. The farmer-facing assistant routes call a local function named `neuGenExplain`, which selects fixed English or Marathi text from the question and returns it as the answer. NuGen URL/key variables only affect status labels; they do not enable inference. No endpoint, model ID, agent ID, request payload, or NuGen authorization header is implemented.

## Findings

| 4 | Is a NuGen API key required? | **Not to use the current assistant.** It returns a local answer without a key. The key is only part of a truthiness check with `NEUGEN_API_URL` (`src/integrations.js:17`); both values being set does not cause a provider call. |

## Farmer UI → backend → provider trace

1. The dashboard and assistant expose explanation/chat controls (`public/app.js:304-306,394-398`). Recommendation cards also render an explanation button (`public/app.js:365`).
2. The button handlers post to the same-origin `/api/ai/explain` or `/api/ai/chat` routes (`public/app.js:763-777,814-828,841-857`) through the browser's `api()` helper (`public/app.js:85-93`).
3. Express requires authentication and farm ownership, then builds a farm bundle. That bundle uses `calculateDecisionEngine` for its structured results (`server.js:162-221,724-770`).
4. Both AI-labelled routes call `neuGenExplain` in `src/integrations.js`. This function creates a fixed string locally. **There is no subsequent NuGen/provider step**, network client call, endpoint resolution, model selection, or authorization header.
5. The explain route records the local answer as an `ai-explanation` decision (`server.js:740-757`); this persistence label does not indicate model provenance.

The regular farmer dashboard data path is separate: `loadDashboard()` requests `/api/dashboard` (`public/app.js:589-612`), which returns the bundle produced by the local Python decision engine (`server.js:393-404,162-221`). No NuGen call participates in that path.

## Configuration and documentation notes

- The NuGen variables appear in `.env.example` and are checked in `src/integrations.js` and status endpoints, but they are not used in an HTTP request.
- `plan.md:17,64` describes a planned/configuration-driven NeuGen adapter and fallback; `docs/API.md` lists the AI-labelled routes. These documentation/configuration references do not establish live inference. The current implementation is authoritative and contains only the local fallback.
- The repository's tests verify the local decision engine and that admin health output does not disclose environment-variable names (`tests/core.test.mjs:27-77`; `tests/admin-dashboard.test.mjs:181-184`). No test exercises a NuGen request or provider response.
- Weather also has an explicitly uncalled provider adapter: `getWeather` says a configured Open-Meteo provider is not called until its inputs/mapping are verified (`src/integrations.js:8-13`). This does not constitute an AI integration.

## Conclusion

The website's AI-labelled farmer features are **demo/local explanation templates**, not live NuGen Intelligence. NuGen has no active HTTP integration in this repository. A genuine integration would require implementing and verifying a provider request, endpoint and model/agent configuration, server-side authentication, response parsing, and tests that establish provider provenance.
